# Опис інтеграції для hand-off

## Роль

Інтеграційний інженер агенції автоматизації, що готує технічний опис workflow
для передачі команді підтримки й клієнту — не код, а зрозумілий документ.

## Мета

За коротким описом n8n-інтеграції (тригер + сервіси + бізнес-мета) написати
структурований технічний документ: тригер, кроки обробки даних, обробка
помилок, де зберігаються креденшели, як перевірити, що інтеграція працює.

## Контекст

- Вхід — короткий бриф інтеграції від project-менеджера чи клієнта (2-5 речень:
  який тригер, які сервіси, яка мета), напр. `docs/sanitized-brief.md`
  (санітизований бриф Task B) або будь-який інший бриф такого самого формату.
- Домен: n8n-workflow'и агенції; креденшели живуть у n8n credential store, а не
  в самому workflow чи документації (той самий принцип, що й у Task B —
  `docs/sanitization-checklist.md`).
- Аудиторія документа: колега, який ніколи не бачив цей workflow, і клієнт,
  якому документ можна показати без NDA-ризику.

## Обмеження

- НІКОЛИ не вписувати реальні токени/URL/webhook-адреси — тільки плейсхолдери
  на кшталт `<SLACK_BOT_TOKEN_OUT_OF_BAND>`.
- Не вигадувати кроки чи сервіси, яких не було у вхідному брифі.
- Максимум одна сторінка — це hand-off документ, не специфікація на 10 сторінок.

## Acceptance criteria

- [x] Документ явно описує факти з брифу (тригер за змістом, сервіс
      призначення, бізнес-мета) і де зберігаються креденшели (домен-політика
      агенції, не деталь брифу).
- [x] Технічні деталі, яких немає в брифі (конкретний механізм тригера,
      обов'язкові поля, формат повідомлення, обробка помилок/retry),
      позначені як «не вказано в брифі», а не вигадані.
- [x] Жодного реального секрету, токена чи URL — лише плейсхолдери.
- [x] Є окрема секція «Як перевірити» з конкретними кроками.
- [x] Документ зрозумілий людині, яка не бачила workflow раніше.

## Формат відповіді

Markdown-документ за структурою: Мета інтеграції / Тригер / Кроки / Обробка
помилок / Креденшели / Як перевірити.

## Stop

Після готового документа — зупинитись. Не пропонувати імплементацію самого
n8n-workflow'у — це окрема задача.

## Результат реального запуску

**Вхідний бриф (синтетичний, для перевірки промпту):**
> «Потрібна автоматизація: коли хтось заповнює форму зворотного зв'язку на
> сайті клієнта, команда продажів має миттєво побачити лід у Slack-каналі
> `#new-leads`, а не чекати на email-розсилку раз на годину.»

**Згенерований документ:**

---

### Лід із сайту → Slack-сповіщення

**Мета інтеграції:** миттєво сповіщати команду продажів про новий лід у
Slack-каналі `#new-leads`, замість email-розсилки з затримкою.

**Тригер:** n8n-workflow, що запускається при відправленні форми зворотного
зв'язку на сайті клієнта. Конкретний механізм (webhook чи інша нода) і
обов'язкові поля форми — **не вказано в брифі**, уточнити з клієнтом перед
імплементацією.

**Кроки обробки:**
1. Workflow отримує дані ліда з форми.
2. Формує повідомлення для Slack-каналу `#new-leads`.

Точний формат повідомлення й перелік полів — **не вказано в брифі**; наведено
мінімальний скелет, достатній для оцінки обсягу робіт.

**Обробка помилок:** бриф не описує поведінку при збої Slack API чи
невалідних даних форми — **не вказано в брифі**. Типове n8n-рішення (retry,
fallback-сповіщення) потребує окремого уточнення з клієнтом перед
імплементацією.

**Креденшели:** Slack Bot Token зберігається в n8n credential store і
підключається до ноди за посиланням на креденшел, **не** вписується у workflow
JSON чи в цей документ — у публічній/клієнтській версії документа він
позначається як `<SLACK_BOT_TOKEN_OUT_OF_BAND>` (стандартна політика агенції,
а не деталь цього брифу).

**Як перевірити:**
1. Спершу уточнити з клієнтом/n8n-командою фактичний механізм тригера і схему
   payload — вони **не вказані в брифі**. Наведений нижче `curl` — лише
   приклад і застосовний **тільки якщо** тригер підтверджено як webhook саме
   з полями `name`/`email`; якщо ні — описати перевірку через реально
   налаштований тригер, а URL і поля позначити «не вказано в брифі».
2. Якщо тригер підтверджено як такий webhook — надіслати тестовий `POST` на
   тестовий webhook-URL з фейковим payload:

   ```bash
   curl --fail-with-body --request POST \
     --header 'Content-Type: application/json' \
     --data '{"name":"Test Lead","email":"test@example.test"}' \
     "$WEBHOOK_TEST_URL_OUT_OF_BAND"
   ```

   Змінна середовища `WEBHOOK_TEST_URL_OUT_OF_BAND` вказує на тестовий, а не
   production, endpoint.
3. Перевірити, що повідомлення з'явилось у тестовому Slack-каналі протягом
   кількох секунд.
4. Перевірити в n8n execution log, що виконання позначено як success.

---

**Підсумок перевірки:** документ явно розділяє факти з брифу (тригер за
змістом, сервіс призначення, бізнес-мета) від технічних деталей, яких бриф не
надає (точний механізм тригера, обов'язкові поля, обробка помилок/retry) —
останні позначені «не вказано в брифі» замість вигаданих подробиць, що
відповідає обмеженню «не вигадувати кроки чи сервіси, яких не було у вхідному
брифі». Документ не містить жодного реального токена чи URL. Крок перевірки
з конкретним `curl`-прикладом — умовний і стане дійсно відтворюваним лише
після підтвердження тригера й схеми payload з клієнтом/n8n-командою; доти це
лише ілюстрація можливої перевірки, а не готовий тест. Промпт
перевикористовний для будь-якої іншої n8n-інтеграції агенції — достатньо
замінити вхідний бриф.
