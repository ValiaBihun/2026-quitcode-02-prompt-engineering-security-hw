# Дебаг баг-репорту по кошторису

## Роль

Інженер, що системно дебажить: спершу відтворює баг мінімальним прикладом,
потім називає root cause конкретним рядком коду, і лише тоді виправляє.

## Мета

Відтворити баг-репорт мінімальним прикладом, назвати root cause конкретним
рядком коду і виправити його разом з регресійним тестом — без зміни
публічного API.

## Контекст

- Баг-репорт: «Клієнту пішов кошторис на **-$250.00**. Ми випадково ввели
  `discountPercent: 150` замість `15` — калькулятор мовчки порахував від'ємну
  суму замість помилки валідації».
- Файл: `app/src/quote.ts`, функція `estimateTotalCents`.
- Тести: `app/src/quote.test.ts`, домен — суми завжди цілі числа в центах,
  `discountPercent` задокументовано як `0..100` (лише в JSDoc, без перевірки
  в рантаймі).

## Обмеження

- НЕ міняти публічний API (`QuoteInput`, сигнатуру `estimateTotalCents`) —
  тільки поведінку при невалідному вводі.
- Мінімальний діф: не рефакторити `splitInstallments` і `formatMoney`.
- Виправлення без регресійного тесту не приймається.

## Acceptance criteria

- [x] Баг відтворено мінімальним прикладом до фіксу (конкретний вхід → конкретний
      неправильний вихід).
- [x] Root cause назвлано явно: файл:рядок і чому саме там.
- [x] Виправлення + тест, що фейлився б без фіксу.
- [x] Заодно перевірено симетричний крайовий випадок (від'ємний відсоток).
- [x] `cd app && npm test` зелений.

## Формат відповіді

Спершу root cause одним абзацом, потім діф, потім результат прогону тестів.

## Stop

Після зеленого прогону з новим тестом — зупинитись. Не додавати валідацію
для `hours`/`rateCents` чи інших полів — це поза межами цього баг-репорту.

## Результат реального запуску

**Відтворення (до фіксу):**

```
estimateTotalCents({ hours: 10, rateCents: 5000, discountPercent: 150 }) === -25000   // -$250.00
estimateTotalCents({ hours: 10, rateCents: 5000, discountPercent: -20 }) === 60000    // більше за gross
```

**Root cause:** [`app/src/quote.ts:20`](../app/src/quote.ts) — `estimateTotalCents`
довіряв `discountPercent` без перевірки діапазону. Коментар типу `QuoteInput`
каже "0..100", але в коді цю умову ніхто не перевіряв, тож помилка введення
(150 замість 15) тихо перетворювалась на від'ємну суму замість явної помилки.

**Виправлення:** додано guard на початку функції —
`if (discountPercent < 0 || discountPercent > 100) throw new RangeError(...)`.
Тепер невалідний ввід падає одразу й голосно, а не їде далі в кошторис клієнту.

**Регресійні тести:** два нові кейси в `describe("estimateTotalCents")` —
`discountPercent: 150` і `discountPercent: -20` — обидва очікують `RangeError`.

**Результат:** `cd app && npm test` → 12/12 тестів зелені (було 10/10 до дебагу).
