# Чек-ліст санітизації даних для роботи з AI

Багаторазовий чек-ліст команди: що шукати в клієнтських документах перед тим,
як віддати їх у промпт, як маскувати і яким інструментом користуватись для
якої категорії. Не переказ одного брифу — застосовний до будь-якого
клієнтського документа агенції.

## 1. Що шукаємо (світлофор)

| Категорія | Приклади | Куди можна |
|---|---|---|
| 🔴 Секрети | API-ключі, токени, connection strings, паролі, n8n credentials | нікуди; лише out-of-band через env |
| 🔴 PII клієнтів | ПІБ, email, телефон, адреса, месенджери | нікуди в публічну модель |
| 🔴 Продакшн-дані | вигрузки таблиць, логи з даними користувачів | нікуди; замінити синтетикою |
| 🟡 Внутрішня комерція | маржа, собівартість, умови угод, стан перемовин | лише no-train / enterprise-тір |
| 🟡 Внутрішня логіка та ідентифікація клієнта | назви систем, схеми БД, ім'я клієнта/компанії | лише no-train / enterprise-тір |
| 🟢 Постановка задачі | опис проблеми, критерії приймання, обсяги без даних | будь-яка модель |

## 2. Як маскуємо

- **redaction** — прибрати повністю: `<REMOVED>`
- **masking** — лишити форму, прибрати значення: `+380 (XX) XXX-XX-XX`, `****-1234`
- **synthetic** — замінити правдоподібним вигаданим: `[CLIENT_1]`, `orders@example.test`
- **out-of-band** — секрет не потрапляє в текст узагалі: `<SECRET_OUT_OF_BAND>`

**Правило:** після маскування задача має лишатись зрозумілою. Якщо модель
більше не розуміє, що робити, — ви замаскували зайве. Постановка задачі й
критерії приймання (🟢) майже завжди можна лишати без змін — саме вони
несуть сенс для AI, а не імена чи ключі.

## 3. Перед тим, як вставити в модель

- [ ] Пройшов пошуком по: `key`, `token`, `secret`, `password`, `postgres://`, `@`
- [ ] Немає жодного справжнього телефону / email / ПІБ / месенджера
- [ ] Вигрузки замінені синтетичними рядками того самого формату (2–3 рядки, не весь датасет)
- [ ] Секрети — лише через env на етапі запуску, не в промпті й не у файлі
- [ ] Назва клієнта замінена на `[CLIENT_N]`, якщо документ не призначений саме для нього
- [ ] Обраний інструмент відповідає **найвищій** категорії, яка лишилась у документі

## 4. Інструмент під категорію

| Категорія | Інструмент / режим | Чому |
|---|---|---|
| 🟢 | звичайна підписка (Claude / ChatGPT, стандартний тір) | публічна постановка задачі — немає що захищати |
| 🟡 | enterprise-підписка з no-train угодою (Claude for Work / Team, ChatGPT Enterprise) або локальна/self-hosted модель | дані ще розкривають бізнес-логіку чи комерцію клієнта — потрібна контрактна гарантія «не тренуємось на ваших даних» і аудит-лог, хто що питав |
| 🔴 | не використовуємо AI взагалі — секрети йдуть лише через env/секрет-менеджер, PII та продакшн-дані обробляються вручну або через внутрішні (не-AI) інструменти | жоден no-train контракт не знижує ризик витоку секрета чи PII до нуля — тут ризик не інструмент, а сам факт передачі даних кудись назовні |

**Чому саме так для 🟡:** для внутрішньої комерції й ідентифікації клієнта
достатньо no-train enterprise-тіру (не потрібна повна відмова від AI, як для
🔴) — постачальник контрактно зобов'язаний не використовувати ці дані для
тренування моделі, і є аудит-лог на випадок перевірки. Локальна модель —
альтернатива, коли навіть enterprise-угоди недостатньо (напр. вимога клієнта
«дані не залишають периметр»), але зазвичай дорожча в підтримці, тож
за замовчуванням команда обирає no-train enterprise-підписку і переходить
на локальну модель лише за окремою вимогою клієнта.
